How Omi is built today

One brain behind every door. A message comes in, one turn writes the reply, and Omi learns from it later in the background. This page shows the parts, how they talk, and what I would improve next.

Code on main, 20 November 2026, commit dc9ecf3f. The live server still runs the 3 November code.

The whole system

The left side is the reply path, where a person is waiting. The right side is background work, where nobody waits. They meet in only two places: the model gateway and the database.

One reply, step by step

A normal reply costs one reply call and one embedding call. Everything else runs only when a fact from code says it is needed.

How Omi learns, after the reply

Nothing here runs while a person waits. Each row is one trigger, the work it starts, what gets saved, and how the next reply uses it.

What to improve

What is solid

  • Reply and learning are separate, so learning never slows a reply.
  • Every memory carries proof lines and dates, checked by code.
  • One function calls the reply model, so swapping models is one setting.
  • Tool results reach the model as data, never as instructions.
  • Each step of a turn is traced and each model call is counted.

What is weak

  • Background jobs run inside the API process, so they stop when the server sleeps.
  • The context engine is the largest part and still mixes old rule code with the new prompt.
  • The full prompt is sent fresh on every reply. Nothing is cached.
  • Nothing here has been judged on real people yet.

In the order I would do them. The first three are small and make everything after them easier to trust.

  1. 1

    Record what really happened in a turn

    The trace saves the model that was asked for, not the one that replied, so a backup reply is invisible. Cost uses one price per provider for the usual models and a per-model table for Claude. Save the real model and use one price table, so cost per reply is right before any model comparison.

    seen in codesmall
  2. 2

    Cache the stable part of the prompt

    Prompt v4 already puts the parts that never change first and this turn's facts last. No request marks that first part for caching. Turning it on cuts most of the input cost of a reply, and matters most if Claude writes replies.

    on the hubseen in codesmall
  3. 3

    Give background work its own worker

    Jobs run in a loop inside the API. On a server that sleeps between requests, memory runs, reminders and nudges stall. A separate worker, or a scheduled wake-up, fixes it. This comes with deploying current main.

    on the hubmedium
  4. 4

    Mark what is live in the context engine

    80 files and about 9,000 lines. Old keyword rules for intent, emotion and stance still sit beside the v4 prompt, and intent rules still feed recall. That goes against letting the model decide. Keep the old code, as agreed, but mark each file live or kept, and move intent off keywords.

    seen in codelarge
  5. 5

    Better recall: keyword index and a daily reflection

    Memory recall is meaning search plus a simple word score. A proper keyword index finds names and rare words that meaning search misses. A daily reflection would turn many small memories into a few lasting ones.

    on the hubmedium
  6. 6

    Carry Claude's own blocks through the tool loop

    The reply path speaks one chat format and the Claude path converts it. Between tool rounds, Claude's thinking is dropped. Fine at low effort. Worth doing only if Claude becomes the main reply model.

    seen in codemediumonly if Claude stays
  7. 7

    Quiet hours before Omi reaches out more

    Follow-ups on events are built but switched off. They need quiet hours and a per-person schedule first.

    on the hubmedium
  8. 8

    Judge it on real chats

    Evals run on made-up people. The plan is 100 real traces labelled by you, and a simple side-by-side review of replies. Both need real users first.

    on the hubneeds users

Safety items (crisis replies, consent for sensitive areas, checks on pictures between matched people) are tracked on the hub and are not architecture changes.
